## Q&A

### 1. How does the NHS Mod-11 check digit work?
Multiply the first 9 digits by weights 10, 9, 8 … 2 and sum. Compute
`11 − (sum mod 11)`. If the result is 11 the check digit is 0; if it is 10
the number can never be valid (no single digit satisfies it); otherwise the
10th digit must equal the result. Example: "4505577104" → weighted sum 216,
216 mod 11 = 7, 11 − 7 = 4 ✓.

### 2. Why does UTR only get format validation?
HMRC's UTR check-digit algorithm is not published — the only public
statement (GDSC) says "the first digit is a check digit" without giving the
math. Implementing a guessed algorithm would be worse than none: it would
reject valid UTRs. The XML docs say "format-only" explicitly so consumers
know the limit.

### 3. Why is VAT format-only when a Mod-97 check exists?
The Mod-97 check applies to old-style 9-digit VAT numbers. HMRC has issued
numbers outside that scheme, so enforcing it would reject genuinely issued
numbers. Format validation (GB/XI + 9 or 12 digits) is the safe common
denominator; registration status needs an HMRC lookup anyway.

### 4. Why accept VAT numbers without a GB prefix?
Forms often ask for the number without the country code. Rejecting
"123456789" would annoy consumers who store digits only. Accepting both
forms and normalizing to uppercase-with-prefix-preserved keeps the library
permissive on input, strict on structure.

### 5. Why is "1234567890" an invalid NHS number (not just wrong check digit)?
Weighted sum = 210, 210 mod 11 = 1, 11 − 1 = 10. A check digit of 10 is
impossible, so the number is structurally invalid — it's not that the last
digit is wrong, it's that no last digit could make it right. The test pins
this edge case.

### 6. What's the difference between validation and verification?
Validation = "could this be real?" (format, checksums). Verification =
"is this real?" (HMRC/Companies House lookup). This library does validation.
A test asserting `IsValid("4505577104")` proves the checksum math, not that
the NHS issued that number. Interviewers like this distinction.

### 7. Why `partial` classes with `GeneratedRegex` again?
Same as M1: compile-time regex generation, no runtime cost, pattern
checked at build. Four more validators, same zero-allocation pattern.

### 8. Why separate static classes per identifier instead of one `Uk` class?
Discoverability and versioning. `NhsNumber.IsValid` reads better than
`Uk.IsValidNhsNumber`, and each identifier can evolve (new overloads, parse
methods) without bloating one god-class. It also maps 1:1 to documentation
pages.

### 9. How do you pick test values for checksum validators?
Hand-verify at least one: I computed "4505577104" (sum 216 → check 4) and
"1111111111" (sum 54 → 54 mod 11 = 10 → check 1) manually before writing
the tests. Never copy "example" numbers from blogs — several published
NHS examples fail their own checksum.

### 10. When would you add a `TryParse` returning a value object?
When callers need to carry a validated number through the domain (e.g. a
`Patient.NhsNumber` property that must always be valid). `IsValid` +
`Normalize` cover the 80% case; a `NhsNumber` struct with a private ctor and
`TryParse` factory is the next step if the library grows domain types.

## Exercise (20 minutes)

**Goal:** feel the difference checksums make.

1. Take "4505577104". Change one digit (any position). Run `IsValid` —
   does it catch it? Try 3 different single-digit changes.
2. Now take a UTR "1234567890" and change one digit. Does `IsValid`
   catch it? (It won't — no checksum.) Write one sentence on what this
   means for data-entry error detection.
3. Compute the NHS check digit for "943476591" by hand (weights 10→2),
   then verify with `NhsNumber.IsValid("943476591" + check)`.
4. Look at `CompaniesHouseNumber` — no checksum at all. In two sentences,
   argue for or against Companies House adding one.

**Success criteria:** you can explain why the NHS number catches typos and
the UTR doesn't, and what that costs HMRC in practice.
