# P3/M3 — NuGet packaging & release: learning pack

Milestone: the library becomes a real distributable package — MIT LICENSE,
rich NuGet metadata (readme, repo URL, symbols), and a release workflow that
publishes to NuGet.org when a GitHub Release is published.

## What changed

- `LICENSE` — MIT, copyright Muhammad Noman 2026 (the csproj already
  declared `PackageLicenseExpression>MIT`; now the file exists to match).
- `src/UkIdentifiers/UkIdentifiers.csproj` — `PackageReadmeFile`,
  `PackageProjectUrl`, `RepositoryType`/`PublishRepositoryUrl` (embeds the
  commit hash in the package), `ContinuousIntegrationBuild` (deterministic),
  `IncludeSymbols` + `snupkg` (debugging support), README+LICENSE packed in.
- `.github/workflows/release.yml` — on Release published: build, test, pack
  with version from the tag (`v0.1.0` → `0.1.0`), push to NuGet.org with the
  `NUGET_API_KEY` secret (`--skip-duplicate` for safe re-runs).
- No source-code changes: packaging is metadata + automation.

## Q&A

### 1. Why does the version come from the Git tag instead of the csproj?
Single source of truth. If the version lived in the csproj, every release
would need a "bump version" commit — noise that can drift from the actual
release. The tag `v0.1.0` *is* the release; the workflow strips the `v` and
passes it to pack. You can't publish 0.1.0 twice by accident.

### 2. What does `PublishRepositoryUrl` do and why does it matter?
It embeds the repository URL *and the exact commit SHA* into the .nupkg.
Anyone can trace a package back to the source it was built from — provenance
for free. Combined with `fetch-depth: 0` in checkout, the commit info is
available at pack time.

### 3. What is `ContinuousIntegrationBuild` and why set it true?
It makes the build deterministic: same inputs → byte-identical outputs
(no timestamps/machine paths embedded). Deterministic packages can be
verified by rebuilding from source — a supply-chain hygiene signal that
costs one MSBuild property.

### 4. Why ship a `.snupkg` symbol package?
Without symbols, consumers debugging into your library see decompiled or
"no source" frames. The snupkg carries PDBs; NuGet.org hosts them and
Visual Studio fetches them on demand. It's the difference between a black
box and a library people trust.

### 5. Why pack the README and LICENSE into the nupkg?
NuGet.org renders the packaged README on the package page — it's your shop
window. The LICENSE file inside the package means the terms travel with
the bits, not just the repo. Both are one `<None Include …>` line each.

### 6. Why `--skip-duplicate` on the push step?
If a release workflow is re-run (you click "Re-run jobs"), a plain push
fails with "package already exists" and the run goes red — alarming but
harmless. `--skip-duplicate` makes re-runs idempotent: already-published
versions are skipped quietly.

### 7. Why run the tests in the release workflow when CI already did?
CI ran on the PR branch; the release workflow runs on the *tag*. Tags can be
moved or created on commits CI never saw. Re-running tests at release time
is cheap insurance that the exact bits being published pass.

### 8. What's the difference between `push` and `pull_request` triggers here?
CI (`ci.yml`) runs on every push/PR to main — fast feedback during
development. Release (`release.yml`) runs only when a Release is *published*
— a deliberate human action. Publishing to a public feed should never happen
as a side effect of pushing code.

### 9. Where does `NUGET_API_KEY` come from and who creates it?
You do, once: nuget.org → account → API Keys → create (scoped to
`UkIdentifiers`, push-only) → GitHub repo → Settings → Secrets → Actions →
`NUGET_API_KEY`. The workflow only references the secret name; the value
never appears in logs or code. That's why publishing needs your explicit
yes — the credential is yours.

### 10. Why MIT for a portfolio library?
Permissive licenses maximize adoption: anyone can use the code, including
commercially, with only attribution. For a portfolio piece, adoption *is*
the goal — downloads and dependents are evidence. Copyleft (GPL) would
require derivative works to be open-sourced, which discourages corporate
use.

## Exercise (20 minutes)

**Goal:** understand what actually ships in a package.

1. Run `dotnet pack src/UkIdentifiers/UkIdentifiers.csproj -c Release -o ./nupkg`
   then unzip the `.nupkg` (it's a zip). List what's inside — find the
   README, LICENSE, XML docs, and the DLL.
2. Open the `.nuspec` inside. Find: version, authors, repository commit,
   license expression. Which of these came from the csproj?
3. Re-run pack twice and compare file hashes (`sha256sum`). Are they
   identical? (They should be — deterministic build.) Now remove
   `<ContinuousIntegrationBuild>true</ContinuousIntegrationBuild>`, rebuild
   twice, compare again. What changed and why?
4. Write down the exact 5 clicks to create the `NUGET_API_KEY` secret
   (don't create it yet — publishing is a separate explicit yes).

**Success criteria:** you can explain what a .nupkg contains, why the
version comes from the tag, and where the API key lives.
